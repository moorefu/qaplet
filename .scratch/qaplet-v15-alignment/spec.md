# v1.5 增量对齐与 M1 入口规格

**Status:** ready-for-agent
**Confirmed:** 2026-11-01，沿用 grill-with-docs 六项决策及最终确认；用户在 to-spec 中确认继续采用共享外部命令、真实制品和现有证据消费者的测试边界。
**Execution state:** 任务 01/02/03 已实现并实际验证：统一 v3、目标 QuickJS/ARM64 overlay 与 Ubuntu ESM/Promise 微型 Host；新配方已晋级 pinned，可进入正式 M1。04/05 继续负责新跨宿主/ABI 与分级 CI，06 保持 needs-info；实际结果见各任务及验收记录，规格发布本身不作为实现成绩。
**Baseline:** [v1.5 实施修订](../../docs/plans/qaplet-v1-implementation-plan-v1.5.md)与 [ADR 0004](../../docs/adr/0004-v15-platform-baseline.md)。

## Problem Statement

维护者准备从已完成的 M0 进入 M1，但当前实现与 v1.5 路线之间存在明确差距：构建仍由分立锁确定输入，QuickJS 不是目标提交，最小 C eval 只执行全局脚本，尚未建立 ESM/Promise 微型 C Host 闭环。直接开始正式 Runtime 和 Qaplet Embed SDK，会使新输入、旧成绩和新增合同混在一起，难以判断哪些前置已经满足。

与此同时，既有 cosmocc 原件、构建缓存、跨宿主探针、离线恢复和 Core gate 已经产生真实证据。维护者需要保留这些投入及失败历史，复用相同输入的已验证事实，并准确列出新组合必须重验的部分。长期镜像、真实平台资源和后续 OS 调度不能被误放成当前全部工作的前置，也不能被当作已经完成。

## Solution

以 v1.5 及已确认修订作为当前路线，在现有 M0 之上实施有序的增量：先统一 v3 构建输入锁，再受控升级目标 QuickJS 并复核 ARM64 补丁，随后完成 ESM/Promise 微型 C Host。三项完成后进入正式 M1；新输入的跨宿主与 ABI 回归、分级 CI 与 M1 的 OS 无关工作并行，约束相应验收及 OS ABI 冻结。

M1 建立 Engine、最小 CLI 和最小可用 Qaplet Embed SDK；跨 OS 唤醒、I/O 取消、迟到 completion 和完整调度由 M2 承接。开发期间可使用逐次校验的现有缓存，长期原 ZIP 镜像及同 SHA 恢复在发布前完成。ARM64 继续原生页覆盖优先，完整系统 QEMU 补缺；保留实际执行方式，不增加物理 ARM64 64K 硬前置。

本规格的实施范围是前置对齐、证据和门禁接入，以及 M1/M2 的阶段边界。正式 M1 的具体 API、预算数值和逐票实施方案在进入其执行规格时细化。

## User Stories

1. 作为维护者，我希望有唯一的当前路线和清晰的阶段入口，以便从已完成 M0 继续推进 v1.5。
2. 作为审核者，我希望旧 M0 的原合同、完成结论和输入身份继续保留，以便判断历史成绩的实际适用范围。
3. 作为后续应用开发者，我希望已完成的服务探针和计划外成果可查阅，以便未来复用系统行为经验。
4. 作为构建者，我希望复用现有相同 cosmocc 原件和证明，以便避免重复选型或追逐滚动 Nightly。
5. 作为构建者，我希望原 ZIP 的长度和完整摘要在使用时重新核验，以便缓存命中不会掩盖损坏或身份漂移。
6. 作为审核者，我希望 Run HEAD、原 ZIP、解压组件、派生工具与 libc 来源证明分别记录，以便不夸大供应链证明等级。
7. 作为开发者，我希望所有构建入口从统一 v3 锁解析输入，以便本地、CI、离线和证据消费者使用同一组合。
8. 作为维护者，我希望旧分锁迁移后不能独立改变版本，以便消除多个权威入口之间的冲突。
9. 作为构建者，我希望未验证的候选输入与可用 pinned 输入有明确区别，以便不把选型样例当成正式构建成绩。
10. 作为开发者，我希望已有缓存内容和可验证布局优先复用，以便锁格式迁移不会引入无必要的目录搬迁。
11. 作为开发者，我希望获取和升级输入是显式动作，以便普通构建不会隐式联网或改变源码。
12. 作为离线使用者，我希望缺少锁定输入时立即得到失败原因，以便系统不会改用其他 Nightly 冒充原件。
13. 作为维护者，我希望缓存验证失败时保留唯一原件和诊断证据，以便恢复操作不会破坏可追溯基线。
14. 作为 Engine 开发者，我希望升级到精确的目标 QuickJS 提交，以便 M1 建立在 v1.5 选择的源码上。
15. 作为审核者，我希望 Commit、Tree、VERSION、原始内容和补丁分别验证，以便相同版本日期不会被当作相同源码。
16. 作为 ARM64 使用者，我希望现有 full-pointer 补丁经过差异复核和实际运行验证，以便升级不会重新引入已知崩溃。
17. 作为维护者，我希望目标源码的许可和来源材料保留，以便后续发行有可核验依据。
18. 作为构建者，我希望源码或补丁变化使不兼容的字节码、对象和构建缓存失效，以便旧产物不会混入新组合。
19. 作为后续 M1 实现者，我希望先有无需正式 SDK 的微型 C Host，以便尽早证明目标引擎与工具链可以协作。
20. 作为测试者，我希望微型 Host 实际加载 ESM 及最小依赖并产生已知结果，以便区分模块闭环与已有全局 eval。
21. 作为测试者，我希望 Promise pending jobs 被实际驱动并完成，以便成功结果能够证明异步任务闭环。
22. 作为开发者，我希望模块错误、job 异常和未完成任务产生可观察的非通过结果，以便失败不会被成功退出掩盖。
23. 作为测试者，我希望每次命令有时限、原始输出、退出码和清理结果，以便可以本地复现失败。
24. 作为发行构建者，我希望制品和 SDK 在 Ubuntu 生成，以便其他平台验证的是所提供的交付物。
25. 作为跨平台使用者，我希望同一 fat APE 的原始字节在不同宿主运行，以便可携带声明有同字节证据支持。
26. 作为审核者，我希望启动 helper、重命名、签名或其他派生交付物有各自身份，以便派生结果不会冒充原始制品。
27. 作为 ARM64 测试者，我希望优先测量原生 runner 的页大小，再用完整系统 QEMU 补缺，以便现有资源可以满足真实内核覆盖。
28. 作为审核者，我希望 guest 输入、内核页大小与 native/emulated-system 标识可核验，以便 qemu-user 或 TCG 结果不会被冒称物理 native。
29. 作为维护者，我希望新引擎和配方重新取得相关跨宿主证据，以便旧成绩不会自动外推到新输入。
30. 作为审核者，我希望缺项、失败、冲突或错误身份的证据被消费者拒绝，以便完整门禁不能通过空结果或跳过获得。
31. 作为贡献者，我希望每次提交有 Linux Fast 检查，以便较早发现输入、构建和最小 Engine 回归。
32. 作为维护者，我希望 PR 的 Cross 检查验证主要宿主同字节运行，并对敏感变更提升测试，以便尽早发现不可移植的设计。
33. 作为发布负责人，我希望 Full 按日或 RC 覆盖已实现的高风险合同，以便资源缺失和未实现功能不会被空门禁冒充通过。
34. 作为构建者，我希望 CI 缓存恢复后仍验证身份且只有可信事件写入可信缓存，以便缓存策略不削弱构建合同。
35. 作为审核者，我希望本地重放、静态 CI 检查和实际远程 run 明确区分，以便不会用另一提交的成绩判定当前变更。
36. 作为后续实现者，我希望任务的前置、阻断范围和验收责任清楚，以便能够从新的会话按顺序继续。
37. 作为嵌入者，我希望 M1 提供版本化 Runtime/Context、模块注册和 eval/run，以便纯 C Host 能形成最小可用嵌入闭环。
38. 作为 SDK 使用者，我希望 JS 操作受 owner-thread 约束，以便跨线程提交不会直接访问 JS 堆。
39. 作为 SDK 使用者，我希望通过有界 POD 队列提交数据并由 owner 主动处理，以便 M1 可在不依赖 OS waker 的情况下嵌入。
40. 作为 SDK 使用者，我希望能发出协作式 stop/interrupt 请求，以便宿主可以控制运行而不提前依赖完整 I/O 取消语义。
41. 作为 Host 开发者，我希望 OS 唤醒、取消、迟到 completion 和完整调度留给 M2 的真实探针，以便不会过早冻结未知 ABI。
42. 作为 M1 开发者，我希望长期镜像尚未落实时仍可使用已验缓存，以便平台开发可以继续。
43. 作为发布负责人，我希望原 ZIP 长期留存并从空缓存按同 SHA 实际恢复，以便上游 Artifact 过期后仍可重建。
44. 作为发布负责人，我希望镜像和必需平台证据未完成时阻断发布，以便规划完成不会被误认为 release-ready。

## Implementation Decisions

1. **阶段基线**：采用 v1.5 与用户确认的六项修订。v1.4、已完成 M0 的 12 张任务、失败记录和服务相关成果继续保留；具体业务应用不进入当前平台交付主线。旧结论只适用于其原输入与原合同。
2. **推进顺序**：任务 01 统一 v3 锁，任务 02 升级目标 QuickJS，任务 03 完成 M0-A ESM/Promise；三项完成后进入正式 M1。任务 04 的新输入跨宿主回归和任务 05 的分级 CI 可与 M1 OS 无关工作并行，约束相应 M1 验收及 Host/SDK OS ABI 冻结。任务 06 是发布前门禁。
3. **统一输入入口**：目标 schema 为 `qaplet.toolchain-lock.v3`，构建、输入校验、离线、CI 和证据消费统一解析身份。旧分锁可以保留作历史或被精确摘要绑定的清单，但不能继续独立选版本。组件清单的摘要算法、字段映射和状态转换由迁移任务明确，不填造未知字段。
4. **候选与 pinned**：`selected_pending_validation` 只允许显式获取和受控基础探针，不签发普通或发行构建成绩。新组合完成统一入口、源码及补丁身份、原件/组件/模式/链接校验和实际工具链/目标引擎探针后才晋级 `pinned`。既有 cosmocc 证明可以复用，但 pinned 不等于 release-ready。
5. **固定工具链**：cosmocc 沿用 Run `41169443573` / Artifact `13031425078`，原 ZIP 长度 `419652152`，SHA-256 为 `f2f984d3a9790674fc0da11c1c00a32d4fe3f8dafde99af74b0c6dc24a2a16cf`。不自动重新选择 Nightly，不以解压目录重打包替代原 ZIP。
6. **来源证明**：Run HEAD 关联、原始归档身份、组件清单、派生 Linux 工具视图与独立 helper 身份分别保留。Run HEAD 不作为已证明的内含 libc 源码身份；没有独立签名 attestation 的事实继续如实记录。
7. **权限与链接**：以实际归档元数据和当前清单为依据。现有原件已记录 3,043 个 file/link 条目、208 symlinks、77 executable entries，未进行权限修复；仅在实际缺失时按审计规则恢复所需语义，不能把无必要的 chmod 当成前置。
8. **QuickJS 受控升级**：从当前 `e621135dc542e000e31038bedc52944aa0adaf1a` 升级到 `2833510432045f72915919cef680ba59e5153b16`。两者 VERSION 同为 `2026-06-04`，仍须分别校验 Commit、Tree、原始内容、许可及有序 patch 身份。现有 ARM64 full-pointer overlay 的保留、适配或移除必须由差异与实际运行支持。
9. **缓存与恢复**：复用主工作区物理缓存根及可验证的已有布局；迁移不强制重排目录。源码/补丁/配方变化更新相应身份并隔离不兼容缓存。物化采用受控 staging 和原子发布，失败保留原数据；缺失或损坏时只接受明确允许的固定原件或同 SHA 来源，离线缺失立即失败。
10. **M0-A 增量**：复用现有 APE builder、输入校验和报告机制，以微型 C Host 验证 ESM、最小依赖加载和 Promise jobs。模块结果、任务完成、异常、超时及退出行为必须可观察；不把已有 global-eval 成绩记成新增合同通过，也不要求先完成正式 SDK 或完整产品 resolver。
11. **构建与分发**：制品和 SDK 在 Ubuntu 构建，其他平台消费所提供字节并验证。跨宿主比较绑定各自制品 SHA、输入、补丁和配方；helper 或其他派生物独立记录，不将不同探针强行视为同一文件。
12. **平台覆盖**：新组合重新验证 Linux x64、Windows x64、macOS x64/ARM64、Linux ARM64 4K/64K 的相应合同。ARM64 原生页覆盖优先，缺失组合可由固定完整系统 QEMU/TCG 补齐；guest 内实际确认架构和页大小，固定 QEMU、machine/CPU、kernel/config/rootfs 身份。qemu-user 不满足该合同，TCG 不外推物理硬件或性能。
13. **证据消费**：复用现有只读消费者，按新输入、制品、OS/架构/页大小和执行方式签发覆盖。报告至少保留实际命令、时间、退出、时限、原始输出及相关身份；缺设备/权限/依赖保持 blocked 或 not_run，选中的失败和必需项缺失不能被后续成功或 skip 覆盖。
14. **分级 CI**：Fast 每提交验证 Linux 输入和已实现的最小功能，Cross 每 PR 验证主要宿主同字节行为并提升 Engine/Host/SDK/锁/patch 敏感变更测试，Full 按日或 RC 覆盖已实现的架构、页配置和高风险合同。共享本地脚本承担行为，workflow 负责调度；不以重命名、空矩阵或未实现用例声明完成。
15. **CI 身份与缓存**：producer/consumer 对应同一提交及实际原字节，记录 run/job/runner image；只对可信事件开放可信缓存写入，恢复后继续验证。fork PR 不依赖注入第三方仓库凭据；固定原件不可取得时明确阻断，不切换来源身份。
16. **M1 边界**：M1 覆盖统一 Runtime/Context Factory、显式 ESM normalize/load、TLA/Promise/jobs、GC/内存/栈/中断预算、最小 CLI、版本化 Qaplet Embed SDK、模块注册及纯 C Host 示例。SDK 使用版本和结构大小约束；具体签名及预算不在本规格中提前冻结。
17. **M1 线程与停止**：JS API 只由 owner thread 使用。M1 包含 owner 主动处理的有界 POD 队列和协作式 stop/interrupt；跨线程仅提交数据或停止请求。跨 OS waker、Reactor/WorkPool、I/O 取消、迟到 completion、Process/TTY 与完整调度由 M2 承接，相关 OS ABI 依据实际探针冻结。
18. **长期留存与发布**：M1 可使用每次重新校验的现有缓存。任务 06 落实独立于可丢弃缓存的长期原 ZIP 留存、访问/保留策略和同 SHA 恢复；存储目标与写入权限尚未确定，保持 needs-info。未通过实际恢复验收不能签发 release-ready，但不阻断 M0-A/M1 开发。
19. **完成语义**：任务状态由各自实际执行、负向测试及证据推进。本规格 ready-for-agent 表示可以按依赖实施，不表示新锁 pinned、新 M0-A/B/C pass、M1 完成或发布就绪。

## Testing Decisions

- **主测试边界已确认**：从共享外部命令进入，观察真实制品或纯 C Host 的执行行为，再由现有结构化证据消费者判断结果、身份与覆盖。优先复用现有入口，避免为各层另建平行测试框架；内部函数布局、调用次数和私有对象形状不属于合同。
- **现有入口的职责保持清楚**：构建与探针入口产生实际运行证据；只读 Core 消费者和严格证据回归入口验证显式选中的现有输入。消费者通过不表示它重新下载、编译或运行了生产者；静态预检也不代替产品执行。
- **统一锁与供应链模块**：通过真实入口验证迁移前后输入一致、本地/CI/离线消费者一致和显式获取。注入未知 schema、缺失/占位字段、冲突旧入口、错摘要、缺组件和 helper 遗漏，要求在供应 executable 使用前拒绝。沿用现有源码、Nightly、构建和离线合同测试的外部行为模式。
- **QuickJS 升级**：验证精确官方对象、干净物化、有序补丁及离线恢复，再实际构建最小 eval/对象/指针/错误用例；至少取得 Ubuntu x64 与实际 ARM64 的关键补丁回归，ARM64 可使用锁定完整 guest。以实际结果支持补丁结论，并拒绝同 VERSION 错源码、dirty 内容、补丁漂移和旧缓存混用。
- **M0-A Host**：真实编译并运行 ESM 导出及依赖的已知结果和 Promise jobs 完成；覆盖模块缺失/语法或求值错误、job 抛错、未完成/超时及错误退出。检查 stdout/stderr、退出码、清理和身份，不以内部 API 调用次数或只有 global-eval 的成功代替。
- **缓存和断网模块**：复用实际隔离、双构建及拒绝用例，验证相同输入可恢复、离线无隐式下载和产物身份。损坏测试使用受控副本或一次性缓存，保留原件；不能删除唯一原 ZIP 来制造负向条件。重算变化影响的输入与配方证据，不继承旧组合的通过状态。
- **跨宿主模块**：Ubuntu 构建一次后交付同字节 APE，复用 startup、native I/O、64K 深探针和 Core gate。重新验证新引擎及变化影响的合同；核对实际 CPU/kernel/page size、执行方式与 helper 身份。guest 的完整串口和固定输入需对应实际执行，qemu-user 或错误页配置必须被拒绝。
- **证据拒绝测试**：沿用现有只读 consumer、分发验证和严格回归中的变异用例，覆盖缺项、重复/冲突报告、错 producer/commit/artifact、改日志/原件、错页大小和 skip 冒充通过。完整证据回归中的必需项不得因无数据或跳过而通过；普通仓库测试中的显式平台 skip 不代表产品覆盖。
- **CI 编排模块**：先本地检查分层触发、敏感路径提升、缓存权限和报告保留，再用实际远程 run/job/commit/runner image 与原始制品验证调度。区分静态检查、本地重放和远程成功；空矩阵、缺必需 job、continue-on-error 掩盖失败和错提交结果不能满足验收。
- **正式 M1 的验收边界**：进入 M1 后，通过版本化 SDK 的纯 C Host 与最小 CLI 验证 ESM/TLA/jobs、重复创建销毁、owner-thread 拒绝、POD 队列有界行为和协作式停止。沿用同一外部行为及证据模式；具体用例、容量和预算在 M1 规格细化，不把 M2 OS 唤醒/取消作为 M1 隐含前置。
- **长期镜像恢复**：存储落实后在一次性空缓存中实际取回原 ZIP，独立核对长度/SHA、物化清单与必要 probe。模拟上游不可用、镜像缺失/损坏/无权限，验证同 SHA 恢复或明确失败；只有 URL 或缓存命中不算完成。
- **阶段验收**：本地探索与失败复现优先，CI 持续回归。01–03 的实际结果决定正式 M1 是否可进入；M1 需要 Linux Fast 和主要宿主 Cross 证据，相关 OS ABI 冻结消费新输入的相应回归。Full 与发布门禁按已实现及公开承诺能力执行，必需资源缺失必须可见并阻断对应结论。

## Out of Scope

- 本轮规格发布时执行锁迁移、源码升级、缓存搬迁、编译、启动 guest、修改 CI 调度或向长期存储上传原件。
- 重开旧 M0 已完成任务、删除旧锁/补丁/失败历史，或把旧成绩改写为新输入和新增合同已通过。
- 为 ARM64 64K 增加物理真机硬前置，使用 qemu-user 代替完整系统 guest，或以 TCG 成绩声明物理 native/性能支持。
- 在 M0-A 前置中实现正式 Runtime/SDK、完整 TLA/resolver、Reactor、Node API、QJB、网络/TLS或大资源产品验收。
- 在本规格中冻结正式 M1 的具体函数签名、队列容量、预算数值和逐票实现方案；只沿用已确认的最小 SDK 边界。
- 把跨 OS waker、I/O 取消、迟到 completion、Process/TTY 和完整调度提前纳入 M1，或在相应探针缺失时冻结 OS ABI。
- 具体服务应用业务、Node 全量兼容、移动 Nightly fallback、尚未讨论的长期存储具体选型或尚未授权的外部存储操作。
- 通过新建平行框架、镜像实现细节的测试、只改 workflow 名称或空成功报告替代实际验收。
